# MCP Protocol and Capability Checklist: PhotoCraft MCP Verified Local Smoke

**Purpose**: Unit tests for requirements writing — validate that 007 requirements/specify a complete, clear, objectively verifiable, and non-brittle MCP stdio verified-local smoke (Option A, stateless) for real `tools/list` discovery plus one safe deterministic `tools/call` (`command_list`). This checklist tests requirement quality, **not** implementation behavior.

**Created**: 2026-11-05  
**Feature**: [spec.md](../spec.md) · [plan.md](../plan.md) · [research.md](../research.md) · [contracts/photocraft-mcp-smoke-contract.md](../contracts/photocraft-mcp-smoke-contract.md) · [quickstart.md](../quickstart.md)  
**Review Ownership**: Feature author/reviewer for 007; implementation/test owners use this to refine requirements before coding; maintainers use it to confirm mock-first/default-CI, safety, and non-AI scope boundaries are unambiguous.  
**Marker Semantics**: `- [ ]` unchecked = requirement quality not yet verified; `- [x]` checked = requirement is present, clear, measurable, and reviewable for the stated concern. `[Gap]` = missing requirement; `[Ambiguity]` = requirement exists but is not objectively verifiable; `[Conflict]` = requirements disagree. ## Transport & Session Semantics

- [x] CHK001 Are stdio JSON-RPC transport/session preconditions for a real local verification run specified with enough precision to distinguish a valid MCP session from ad hoc process I/O (client-launched subprocess, stdin/stdout protocol framing, stderr diagnostic-only, bounded lifecycle)? [Completeness, Spec §FR-002, Spec §FR-004, Plan, Contracts §4, Contracts §5.5, Research C3] — Evidence: Spec FR-002/FR-004 require real MCP session + bounded/safe controls; Contract §4 requires use of existing 006 adapter path (stdio framing/timeout/cleanup/FR-006 semantics) and §5.5 preserves 006 §9 session invariants (stdout protocol-only, stderr diagnostic-only, bounded cleanup); Research C3 cites adapter stateless stdio behavior.
- [x] CHK002 Is JSON-RPC request/response correlation quality defined so requirements can objectively verify that discovery/invocation outcomes are matched to the correct request (id/correlation expectations, no stdout contamination assumptions)? [Clarity, Ambiguity, Spec §FR-006, Contracts §4, Contracts §5.5, Gap] — Evidence: Contract §4/§5.5 require reuse of 006 adapter framing/correlation/cleanup semantics and forbid divergent ad hoc client; 006 session invariants (preserved) include JSON-RPC id correlation and stdout protocol-only handling. 007 treats transport/protocol mismatch as FR-006 invalid_response/structured failure.
- [x] CHK003 Are session lifecycle boundaries (initialize/capability negotiation assumptions, per-call session behavior, and shutdown/cleanup expectations) specified consistently between “one real MCP session can perform discovery and invocation” language and the stateless-per-adapter-call boundary? [Consistency, Spec §FR-002, Spec §FR-008, Contracts §1, Contracts §4, Research C3] — Evidence: Spec FR-002 requires discovery+one safe invocation using existing MCP integration behavior; FR-008/edge case 67 and Contract §1/§4 state each adapter call is a full stdio session per call (no session reuse, no cross-call state/artifact cycle). Data Model §2 makes `stateless_per_call` the invariant for the verification sequence.
- [x] CHK004 Are bounded timeout and teardown requirements measurable for startup, `tools/list`, `tools/call`, and overall verification so “stops within bounded limits” cannot be interpreted as best-effort? [Measurability, Spec §FR-004, Spec §User Story 2, SC-003, Contracts §3.1, Contracts §3.2] — Evidence: Spec FR-004/SC-003 require bounded execution and actionable outcomes without unsafe leakage; Contract §3.1 requires bounded startup/call/overall verification and safe cleanup on timeout paths; §3.2 defines bounded timeout inputs/defaults with no unbounded waits.

## Discovery (`tools/list`) Requirements

- [x] CHK005 Are `tools/list` discovery success requirements defined as objectively verifiable outcomes (transport/protocol completion without failure and capability presence) rather than implementation-internal steps? [Clarity, Spec §FR-002, Spec §User Story 1, SC-001, Contracts §4.1, Contracts §6] — Evidence: Spec FR-002/SC-001 require real capability discovery and evidence; Contract §4.1/§6 require `tools/list` completion without transport/protocol failure and version-tolerant capability presence (`command_list`).
- [x] CHK006 Is the minimal required discovery capability explicitly specified as presence of `command_list`, with clear treatment of related tools (`command_run`/others) as observable-but-not-required for pass criteria? [Completeness, Spec §FR-002, Spec §Edge Cases, Contracts §4.1, Contracts §6, Research C3] — Evidence: Contract §1/§4.1/§6 name `command_list` as required presence/minimal pass criterion; full catalog/tool count/order and other tools are explicitly non-required/forbidden as brittle pass criteria.
- [x] CHK007 Are defensive acceptance requirements for discovery payload shapes (direct tools list, result object, adapter-normalized success shape) specified so version/adapter-normalization differences do not create ambiguous pass/fail criteria? [Coverage, Spec §FR-002, Contracts §4.1, Contracts §4.3, Gap] — Evidence: Contract §4.1 requires defensive acceptance of discovery payload shapes consistent with 006 adapter behavior; §4.3 generalizes adapter-normalized/JSON-RPC/content/structured parseable acceptance and error-shape handling.
- [x] CHK008 Are discovery failure requirements specified for “missing capability” as a structured, diagnosable outcome with observed tool context, distinct from transport/protocol failure and generic invalid response? [Completeness, Spec §FR-006, Spec §Edge Cases, Contracts §3.3, Contracts §6, FR] — Evidence: Spec FR-006/edge case 64–65; Contract §3.3 maps missing capability to `mcp_missing_capability` structured failure (actionable, version-tolerant, observed context) distinct from timeout/invalid response/tool error; §6/§7 require reason/observed context in evidence.

## Deterministic Invocation (`command_list`)

- [x] CHK009 Is the verified invocation precisely scoped to `tools/call` name=`command_list` as a safe deterministic engine/editor discovery operation, with objectively verifiable non-error completion criteria? [Clarity, Spec §FR-002, Spec §FR-003, Spec §FR-009, Contracts §1, Contracts §4.2, Research C3] — Evidence: Spec FR-002/FR-003/FR-009; Contract §1/§4.2 define primary safe invocation as `tools/call` `command_list` (engine/editor discovery), requiring non-error parseable/normalizable structured result.
- [x] CHK010 Are invocation argument-safety requirements specified (minimal/safe arguments, no document-mutating/export paths, no user data, no generation prompts) so “safe deterministic invocation” is auditable from requirements? [Completeness, Security, Spec §FR-003, Spec §FR-004, Contracts §4.2, Gap] — Evidence: Contract §4.2 requires minimal/safe args (empty `{}`/safe no-op), forbids document-mutating/export paths, user data, and generation prompts; Spec FR-003/FR-004 require deterministic non-destructive/safely contained behavior and safety controls.
- [x] CHK011 Are requirements explicit that `command_list`/engine discovery evidence MUST NOT be interpreted as prompt-based AI generation/provider/model support, including in success summaries and runbook evidence? [Consistency, Spec §FR-003, Spec §FR-008, Contracts §1, Contracts §4.2, Contracts §7, Research C3] — Evidence: Spec FR-003/FR-008; Contract §1/§4.2/§7/§8 and Quickstart/evidence template require engine/editor automation only, no AI generation/provider/model claim, and evidence fields include non-AI/stateless limits.

## Result/Payload Parsing & Normalization

- [x] CHK012 Are defensive parsing requirements defined for all expected MCP/adapter result envelopes: `result.content` text items containing serialized JSON, optional `structuredContent`, adapter-normalized success, and alternate non-error parseable shapes? [Completeness, Spec §Edge Cases, Spec §FR-002, Contracts §4.3, Contracts §6, Research C3] — Evidence: Spec edge case 66; Contract §4.3/§6 explicitly accept adapter-normalized success, JSON-RPC `result`, MCP `content` text/serialized parseable payloads, and `structuredContent`/alternate non-error parseable shapes defensively.
- [x] CHK013 Is the minimum “normalizable structure” for a `command_list` success objectively specified (what evidence is sufficient) without requiring brittle deep schema equality or exact command catalog contents? [Measurability, Ambiguity, SC-001, Contracts §4.3, Contracts §6, Research C3] — Evidence: Contract §4.3 states a non-error parseable/normalizable structure from safe `command_list` is sufficient evidence and forbids brittle deep schema equality; §6/Quickstart require result-shape summary, not exact catalog contents/count.
- [x] CHK014 Are protocol/tool error signal requirements specified so parsing/normalization can distinguish JSON-RPC/protocol errors, MCP tool `isError`/error payloads, adapter structured failures, and missing/invalid result shapes? [Clarity, Spec §FR-006, Contracts §4.3, Contracts §5, Gap] — Evidence: Contract §4.3 requires defensive handling of protocol failures, `isError`/error payloads, adapter structured failures, and missing/invalid result shapes; §3.3/§5 map them to FR-006 reasons with actionable outcomes.
- [x] CHK015 Are evidence/log redaction requirements specified for parsed payloads, stderr, resolved paths, and config context to prevent secrets/PII/sensitive raw content leakage while preserving diagnosability? [Security, Non-Functional, Spec §FR-004, Plan §Constraints, Contracts §3.1, Contracts §4.3, Gap] — Evidence: Plan constraints require no secrets/PII in logs/evidence; Contract §3.1/§4.3/§5 require secret-safe recording, redaction/avoidance of raw sensitive stderr/config/payload dumps, while preserving bounded diagnostics, resolved path/version context, and actionable summaries.

## Version Tolerance & Non-Brittleness

- [x] CHK016 Are non-brittle assertion boundaries explicitly enumerated: no exact tool count, no full catalog equality, no ordering, no exact command list contents/count across versions, no version/timestamp/AI-output field requirements except as optional evidence? [Completeness, Spec §Edge Cases, Contracts §4.1, Contracts §6, Research C3] — Evidence: Spec edge cases/assumptions; Contract §4.1/§4.2/§6 and Quickstart/Plan enumerate forbidden brittle assertions and allow optional evidence (e.g. observed count/version) only as non-gating context.
- [x] CHK017 Is capability-presence/version-tolerance behavior specified for tool-set variation across PhotoCraft versions, including actionable structured skip/failure when required capabilities are absent or differ? [Coverage, Spec §Edge Cases, Spec §FR-006, SC-003, Contracts §3.3, Contracts §4.1] — Evidence: Spec edge case 64 and FR-006/SC-003; Contract §3.3/§4.1 require minimal presence checks (`command_list`) and structured `mcp_missing_capability`/actionable skip-failure with observed tool context for absent/differing required capability.
- [x] CHK018 Are flaky-test avoidance requirements stated as requirement-quality constraints (deterministic safe invocation, bounded waits, no default-CI real-server dependency, isolated temp roots, defensive parsing) rather than left as implementation preference? [Measurability, Spec §FR-001, Spec §FR-004, SC-002, SC-003, Plan §Testing, Research C2, Research C3] — Evidence: Spec FR-001/FR-004/SC-002/SC-003, Plan testing/constraints, Contract §3.1/§4/§6, and Research C2/C3 require opt-in exclusion from default CI, deterministic safe `command_list` smoke, bounded timeouts, isolated temp roots, cleanup, and defensive/version-tolerant parsing.
- [x] CHK019 Are optional-evidence fields (observed tool count, version/binary identity, sanitized excerpt/digest) clearly classified as non-gating evidence so they cannot become accidental pass/fail criteria? [Clarity, Spec §FR-007, Contracts §6, Contracts §7, Research C4] — Evidence: Contract §6 states observed tool count allowed as evidence but not pass criterion and forbids exact catalog/count assertions; §7/Quickstart/Research C4 treat version/binary identity and summaries as evidence fields when available, with “unavailable/unknown” recorded explicitly rather than gating success beyond required criteria.

## Stateless Boundary & Scope Limits

- [x] CHK020 Is the stateless adapter boundary specified unambiguously as per-call MCP session/no session reuse/no cross-call state, including the explicit exclusion of `doc_new→command→doc_export` artifact-producing cycles? [Completeness, Spec §FR-008, Spec §FR-009, Spec §Edge Cases, Contracts §1, Contracts §8, Research C3] — Evidence: Spec FR-008/FR-009/edge case 67; Contract §1/§4/§8; Data Model `stateless_per_call`; Quickstart/manual smoke sequence and limits all exclude session reuse and artifact-producing cycles.
- [x] CHK021 Are scope boundaries complete for preserving mock-first defaults and public contracts (optional/opt-in only, excluded from default CI, schemas/CLI/fallback/FR-005/FR-006 unchanged, no silent reroute)? [Consistency, Spec §FR-001, Spec §FR-005, SC-002, SC-005, Contracts §2, Contracts §3.3] — Evidence: Spec FR-001/FR-005/SC-002/SC-005 and Contract §2/§3.3/§8 preserve mock-first/default exclusion, all named public contracts, and explicit-MCP no silent reroute.
- [x] CHK022 Are PhotoCraft headless root-semantics requirements specified with safe absolute-root authority boundaries (read/write roots, least privilege, temp default/cleanup, explicit authorized override handling) consistent with local MCP filesystem-authority behavior? [Completeness, Security, Spec §FR-004, Spec §Edge Cases, Contracts §1, Contracts §3.1, Research C1, Research C2] — Evidence: Spec FR-004/edge case 68; Contract §1/§3.1 require absolute safe read/write boundaries, least-privilege temp auto roots with cleanup, explicit authorized maintainer-managed overrides never auto-deleted, and actionable failure for unsafe/misconfigured roots; Research C2 cites PhotoCraft root authority.
- [x] CHK023 Are local MCP capability-limit requirements complete and prominent: engine/editor automation in scope; AI generation/providers/models, bridge/UI broad coverage, and stateful session helper out of scope unless separately evidenced? [Clarity, Spec §FR-003, Spec §FR-008, SC-004, Contracts §1, Contracts §8] — Evidence: Spec FR-003/FR-008/SC-004 and Contract §1/§4.2/§7/§8 state engine/editor automation only and explicitly exclude AI generation/providers/models, bridge/UI/progress/cancellation broad coverage, and stateful session helper/artifact cycle unless separately scoped/evidenced.

## Notes

- This checklist validates **requirement quality** for 007 (Option A). It does not verify test pass/fail, implementation correctness, or real PhotoCraft runtime behavior.
- Preserve 007 guardrails when refining requirements: real-server verification remains optional and excluded from default CI; mock-first/default validation remains unchanged; no prompt-based AI generation/provider/model claim via local PhotoCraft MCP; no stateful cross-call artifact cycle; no public schema/CLI/fallback/FR-005/FR-006 contract changes.
