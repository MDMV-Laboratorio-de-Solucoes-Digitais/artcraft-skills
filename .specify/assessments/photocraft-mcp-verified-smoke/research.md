# Idea Research: PhotoCraft MCP verified local smoke and one deterministic headless capability mapping

- **Slug**: photocraft-mcp-verified-smoke
- **Created**: 2026-11-05
- **Evidence confidence (overall)**: medium-high for local MCP stdio/tool discovery and safety constraints; medium for selecting the best deterministic mapped capability; low for assuming prompt-based AI generation via local PhotoCraft MCP.

## Users & Demand

- **Maintainers/contributors need trustworthy integration evidence, not only mocks.** The repo already has functional MCP stdio in mock-first scope (006, `mcp_tools_list`/`mcp_tools_call`, FR-005/FR-006) and green default tests (399 passed, 1 deselected) but no routinely executed proof against a real PhotoCraft server. A verified local smoke reduces integration risk before broader mapping. — [source: local repo `specs/006-mcp-stdio-functional-integration/*`, `docs/research/2026-11-05-ecosystem-and-status.md`, test run 2026-11-05] (confidence: high, observed).
- **Agent/skill users need deterministic behavior and honest capability boundaries.** PhotoCraft MCP exposes engine/editor commands and document tools; presenting that as prompt-based AI generation would mislead users. Demand is for a *real, useful, deterministic* slice, not inflated generation claims. — [source: https://raw.githubusercontent.com/storytold/photocraft/main/docs/mcp.md; local `photocraft-cli commands`/MCP probe 2026-11-05] (confidence: high, observed/cited).
- **Adoption of agentskills.io/MCP workflows creates pressure for real interoperability evidence** (stated/ecosystem). Skills/MCP are increasingly used to connect agents to tools; local stdio MCP servers are common for developer tools. — [source: https://agentskills.io/specification.md, https://modelcontextprotocol.io/specification/2025-11-25/basic/transports.md, https://modelcontextprotocol.io/llms.txt] (confidence: medium, ecosystem signal).

## Prior Art

- **Internal (006 MCP stdio, mock-first):** adapter implements minimal synchronous stdio JSON-RPC client with `initialize`/`tools/list`/`tools/call`, stdout protocol-only, stderr diagnostics, bounded timeout, request-id correlation, safe subprocess cleanup. `CreativeSkill` has MCP hooks/selection and FR-006 failure metadata. Deterministic fake server covers scenarios. — [source: `skills/core/artcraft_app_client.py`, `skills/core/creative_skill.py`, `tests/_helpers/fake_mcp_stdio_server.py`, `specs/006-mcp-stdio-functional-integration/quickstart.md`] (confidence: high).
- **Internal (006 asset-generation fallback / PR #109, reconciled):** `generate_via_editing_commands` fallback exists and is reconciled with MCP stdio API. This shows deterministic editing/export fallback is already a pragmatic pattern, but it is CLI/edit-command oriented and separate from proving MCP server interoperability. — [source: `skills/core/artcraft_app_client.py`, `skills/core/creative_skill.py`, `specs/006-integracao-geracao-assets/tasks.md`] (confidence: high).
- **Local verified real probe (2026-11-05, safe temp roots):** `/usr/bin/photocraft-cli 0.20.1` (`photocraft-cli --version`, `--help`, `mcp --help`) was available. Using `skills.core.artcraft_app_client` with `photocraft-cli mcp --automation-read-root <tmp> --automation-write-root <tmp>` returned **26 MCP tools** from `tools/list` including `command_list`, `command_run`, `command_batch`, `doc_new/open/save/export/inspect/render_preview`, `jobs_*`, `session_list`, and UI/bridge tools. `tools/call name=command_list` returned engine command metadata (e.g., `file.new`, `edit.fill`, `paint.stroke`; export-related ids included `file.export.quickExport`, `layer.exportAs`, `doc.export`/tool surface present). `tools/call name=doc_new` returned `{"content":[{"type":"text","text":"{\"document\":0}"}],"isError":false}`. A subsequent `doc_inspect` call (new adapter process/session) reported `document:null` and empty session — confirming **current adapter is stateless per call/process**, so multi-step document cycles are not preserved across separate `mcp_tools_call` invocations without a session-capable transport wrapper. — [source: local command outputs in session; temp roots created under `/tmp` and removed after probe] (confidence: high, observed).
- **PhotoCraft MCP contract (primary):** official docs describe headless MCP with read/write automation roots, explicit root semantics, engine-oriented tools/resources, progress/cancellation, `isError` tool failures, JSON-RPC parse errors, and security constraints (safe save/overwrite rules, exports refuse overwrite in specific cases, roots scope filesystem authority). Bridge mode differs (roots/token managed by desktop app). — [source: https://raw.githubusercontent.com/storytold/photocraft/main/docs/mcp.md, https://raw.githubusercontent.com/storytold/photocraft/main/docs/control-protocol.md] (confidence: high).
- **MCP protocol constraints (primary):** stdio requires newline-delimited JSON-RPC, stdout protocol-only, stderr diagnostics; lifecycle begins with `initialize` then `notifications/initialized`; `tools/list` and `tools/call` are standard server methods. Implementations should enforce timeouts and clean shutdown. — [source: https://modelcontextprotocol.io/specification/2025-11-25/basic/transports.md, https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle.md, https://modelcontextprotocol.io/specification/2025-11-25/server/tools.md] (confidence: high).
- **MCP Inspector/mcpdo (tooling context):** official MCP docs/tools include Inspector (web/CLI/TUI), `mcpdo` connection client, and security guidance. These can inform manual/optional debugging and reproducible local checks, but they are not required for the repo’s in-process adapter smoke. — [source: https://modelcontextprotocol.io/llms.txt (`docs/*/tools/inspector*`, `mcpdo`, security)] (confidence: medium, relevant but not directly executed in repo).

## Market & Context

- **Local real smoke is a low-cost de-risking step.** The adapter already speaks MCP to a fake server; validating against a real local binary catches framing/handshake/tool-shape mismatches early, especially because PhotoCraft returns tool results in MCP `content` form and has engine-oriented command semantics. — [source: local probe; PhotoCraft MCP docs; MCP tools spec] (confidence: high).
- **Cost of doing nothing:** MCP remains “green by mock” only; future mapping work may build on incorrect assumptions about real tool shapes, session semantics, roots, export behavior, or progress/cancellation. — [source: 006 quickstart limits; local stateless-per-call finding] (confidence: high).
- **Alternatives users cope with today:** CLI path (`photocraft-cli run/commands/convert/...`) and editing-command fallback; direct MCP client usage outside the skill layer. These work in parts but do not prove the skill adapter’s real MCP path. — [source: `photocraft-cli --help`, repo adapter/skills, PhotoCraft docs] (confidence: high).
- **External ArtCraft/Crafting Apps ecosystem context (sinal):** PhotoCraft/PdfCraft and related Crafting Apps are presented as Rust apps with CLI/MCP/automation surfaces; third-party/community guides may lag or vary by version. Treat as context, not normative contracts for this repo. — [source: https://github.com/storytold/photocraft, https://raw.githubusercontent.com/storytold/photocraft/main/docs/mcp.md; search results from github.com/community guides 2026] (confidence: medium).

## Data & Constraints

- **Protocol/tool-shape constraint:** PhotoCraft MCP tool results observed as `{"content":[{"type":"text","text":"...json..."}],"isError":false}`. Adapter normalization/mapping must parse MCP `content`/`structured` result forms defensively (already a 006 concern) and not assume flat custom keys. — [source: local probe; MCP tools spec result/content model] (confidence: high).
- **Session/state constraint (important):** current 006 adapter performs one stdio subprocess + handshake + single operation per `mcp_tools_list`/`mcp_tools_call`. Therefore a real multi-step cycle (`doc_new` → command → `doc_export`) **cannot be reliably executed as separate adapter calls today**; it requires either (a) a session-capable adapter API (multiple calls over one subprocess/session), (b) use of PhotoCraft `command_batch`/composite tool flow where supported, or (c) limiting the real smoke to stateless discovery/call checks. — [source: `skills/core/artcraft_app_client.py` implementation; local `doc_new`/`doc_inspect` probe] (confidence: high).
- **Safety constraint:** headless PhotoCraft MCP needs explicit `--automation-read-root`/`--automation-write-root`; roots grant filesystem authority. Use temp absolute roots, least privilege, explicit opt-in env var, explicit binary path override, bounded timeout, cleanup, and never run in default CI. PhotoCraft docs warn about overwrite behavior/safe formats and exports; keep smoke operations non-destructive and contained. — [source: PhotoCraft `docs/mcp.md`; MCP security/local-server guidance in llms index] (confidence: high).
- **Capability constraint:** PhotoCraft commands/tools are engine/editor oriented (`file.new`, `edit.fill`, `paint.stroke`, `doc_*`, export commands). There is **no evidence in the consulted primary docs/probe** that local PhotoCraft MCP provides prompt-to-image AI generation equivalent to ArtCraft AI studio/provider generation. Mapping must not claim AI generation. — [source: PhotoCraft `docs/mcp.md`, `docs/control-protocol.md`, local command/tool probe] (confidence: high).
- **Determinism constraint:** optional real smoke may vary by installed PhotoCraft version, enabled commands, fonts/plugins, OS, and filesystem permissions. Keep assertions minimal/stable (`tools/list` contains `command_list`/`command_run`; `command_list` returns parseable command data; tool call returns non-error shape) unless a tightly controlled artifact cycle is designed. — [source: PhotoCraft docs/engine variability; integration-test best practice] (confidence: medium).
- **Version signal:** local verified binary `photocraft-cli 0.20.1 (2026-11-03)`; PhotoCraft docs on `main`/v0.8.x+ have evolved. Optional smoke should record version (`--version`) and treat unsupported capabilities as skipped/structured failures with evidence. — [source: local `photocraft-cli --version`; PhotoCraft repo/docs refs] (confidence: medium-high).

## Evidence Against the Idea

- **Stateful artifact cycle is currently awkward with the adapter.** Because each `mcp_tools_call` creates a new MCP subprocess/session, a file-producing `doc_new→...→doc_export` proof cannot be done by naïve sequential adapter calls. Implementing a session API or using a suitable composite call adds scope beyond a tiny smoke. — [source: adapter implementation; local probe] (confidence: high).
- **Risk of false confidence from narrow smoke.** `tools/list` + `command_list` proves discovery and basic invocation, but not full document mutation/export semantics, progress/cancellation, bridge mode, or AI-style generation. Overstating success would be misleading. — [source: 006 scope; PhotoCraft MCP capabilities] (confidence: high).
- **Environment coupling.** Real smoke depends on a local binary and writable temp roots; version/capability drift can make assertions flaky if too specific. Default CI must remain mock-first. — [source: repo pytest config; PhotoCraft version/docs variability] (confidence: high).
- **Mapping the “wrong” capability can create product debt.** If a CreativeSkill is mapped to a PhotoCraft engine command that does not correspond to the skill’s public promise (especially image generation), schemas/UX semantics become confusing. A narrow, honestly named deterministic capability is safer. — [source: skill schema contracts; PhotoCraft engine-oriented model] (confidence: medium-high).
